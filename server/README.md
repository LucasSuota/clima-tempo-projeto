# server

> API do ClimaFácil (Express 5 + TypeScript `strict`, SQL puro com `pg`, `zod`). Hoje tem o esqueleto (`GET /api/health`), as regras de domínio puras quatro recursos completos (`owners`, `clients`, `quotes` e `follow-ups`, este aninhado em `/api/quotes/:id/follow-ups`) e os indicadores (`GET /api/indicators`).

## Responsabilidade

Sobe o servidor HTTP, valida o ambiente, monta o Express e traduz erros para o formato único da API (AGENTS.md §5.3).
As regras de negócio vivem em `src/domain/` (funções puras, sem I/O; veja [src/domain/README.md](src/domain/README.md)). Todos os recursos percorrem as camadas (rota, serviço, repositório, domínio). Os serviços de `quotes` e `follow-ups` recebem o relógio (`now`) e `staleDays` por parâmetro, calculam status efetivo e "parado" com o domínio e aplicam as transições (AGENTS.md §1, etapa 2).

## Estrutura-alvo

> Organização do código (AGENTS.md §5.2). O código existente já segue esta organização; a tabela "O que tem aqui" lista o que existe hoje.

```
src/
├── index.ts, app.ts, config.ts, db.ts, errors.ts
├── middlewares/    # cors.ts, error-handler.ts
├── domain/         # puro; uma pasta por recurso (quotes, follow-ups, indicators, owners, clients) e shared/ (calendar-date.ts)
├── repositories/   # único lugar com SQL; <recurso>-repository.ts
├── services/       # casos de uso; <recurso>-service.ts
└── routes/         # index.ts (monta /api), health.ts, <recurso>.ts com os schemas zod
test/               # espelha src/: domain/, routes/, middlewares/, config.test.ts, helpers/ (existe: `test-database.ts`)
```

Regras:

1. Na raiz de `src/` só `index`, `app`, `config`, `db`, `errors` e as pastas; nada de `utils.ts`, `helpers.ts` ou `types.ts` soltos.
2. Tipos do domínio em `domain/<recurso>/`; tipos do contrato HTTP inferidos dos schemas zod nas `routes/`.
3. Schemas zod no arquivo do router; acima de ~80 linhas, extrair para `<recurso>-schemas.ts` na mesma pasta.
4. Recurso novo = um arquivo (no `domain/`, uma pasta) em cada camada, com o mesmo nome-base.
5. Só `routes/`, `middlewares/` e `app.ts` importam `express`; só `db.ts` e `repositories/` usam `pg` em execução (`import type { Pool }` é permitido onde o `Pool` chega por parâmetro); `domain/` não importa nada de fora de `domain/`, exceto os erros de `errors.ts`.

## Como se conecta

- **Depende de:** `express`, `pg`, `zod`; `routes/health.ts` recebe o `Pool` por parâmetro; `app.ts` importa `middlewares/error-handler.ts`, `routes/index.ts`, os serviços e os repositórios dos recursos e dos indicadores; `routes/indicators.ts` → `services/indicator-service.ts` → `repositories/indicator-repository.ts`, `services/quote-service.ts` (só `listStaleQuotes`), `domain/indicators/` e `OPEN_STATUSES` de `domain/quotes/quote-status.ts`; `routes/quotes.ts` → `services/quote-service.ts` → `repositories/quote-repository.ts`, `client-repository.ts`, `owner-repository.ts` (só `existsById`) e `domain/quotes/`; `routes/follow-ups.ts` → `services/follow-up-service.ts` → `repositories/follow-up-repository.ts`, `quote-repository.ts` e `domain/follow-ups/`; `routes/follow-ups.ts` importa `parseId` e `calendarDateSchema` de `routes/quotes.ts`; `routes/owners.ts` → `services/owner-service.ts` → `repositories/owner-repository.ts` → `domain/owners/owner.ts`; `routes/clients.ts` → `services/client-service.ts` → `repositories/client-repository.ts` → `domain/clients/client.ts` (o repositório também importa `ValidationError` e `ClientHasQuotesError` de `errors.ts`); `middlewares/error-handler.ts` importa `errors.ts`; `domain/` importa só a si mesmo e `errors.ts` (nenhum import de `express`, `pg` ou `config.ts`).
- **É usado por:** o `web/` (chama `/api` pelo proxy do Vite em dev e pelo nginx no Docker) e o serviço `server` do `docker-compose.yml` (usa o `Dockerfile` desta pasta).
- **Contratos e dados:** `GET /api/health`; erro sempre `{ "detail", "errors": [{ "field", "message" }] }`. Tabelas `owners`, `clients`, `quotes` e `follow_ups`.
  - `GET /api/owners`: 200 com `{ "items": [{ "id", "name", "role" }], "total" }`, ordenado por nome. `id` é `number`.
  - `POST /api/owners`: corpo `{ "name", "role" }` (`name` até 120 caracteres, `role` até 80, ambos obrigatórios e aparados); 201 com o responsável criado; 422 com o formato de erro único se inválido.
  - `GET /api/clients`: 200 com `{ "items": [{ "id", "name", "email", "phone" }], "total" }`, ordenado por `name`, `id`. `id` é `number`; `email` e `phone` podem ser `null`.
  - `POST /api/clients`: corpo `{ "name", "email?", "phone?" }`; 201 com o cliente criado. `name` obrigatório, aparado, até 120. `email`: ausente, `null` ou `''` vira `null`; senão aparado, em minúsculas, até 254 e válido. `phone`: ausente, `null` ou `''` vira `null`; aceita só `0-9`, espaço, `(`, `)`, `+` e `-`, é gravado só com dígitos e deve ter de 10 a 15. E-mail ou telefone repetido: 422 com `"E-mail já cadastrado"` / `"Telefone já cadastrado"` no campo correspondente.
  - `PUT /api/clients/:id`: substitui o cliente; mesmo corpo e mesma normalização do `POST`, e `email`/`phone` ausentes viram `null`. 200 com o cliente. Id inexistente ou malformado: 404 `"Cliente não encontrado"` (o id é validado antes do corpo). Duplicidade com outro cliente: 422 por campo; manter o próprio e-mail/telefone é aceito.
  - `DELETE /api/clients/:id`: 204 sem corpo. 404 se não existir. Cliente com orçamentos: 422 com `"Não é possível excluir um cliente que possui orçamentos"` (`errors` vazio), pela FK `quotes_client_id_fkey`, sem pré-checagem.
  - Resposta de orçamento (`QuoteResponse`): `{ id, description, total, status, sentAt, isStale, daysWithoutContact, client: { id, name }, owner: { id, name, role } }`. `total` é `number`; `status` é o efetivo (um `sent` parado aparece como `no_response`); `sentAt` é `'YYYY-MM-DD'` ou `null`; `daysWithoutContact` é `null` fora dos status abertos.
  - `GET /api/quotes`: 200 com `{ items, total }`, do mais novo para o mais antigo (`created_at`, `id`). `GET /api/quotes/:id`: 200 ou 404 `"Orçamento não encontrado"`; id malformado também dá 404.
  - `GET /api/quotes/stale`: fila de contato. 200 com `{ items, total }` no mesmo `QuoteResponse`, só com `isStale` verdadeiro, ordenada por `daysWithoutContact` decrescente, depois `total` decrescente e `id` crescente. Sem filtro por responsável; lista vazia dá 200 com `items: []`.
  - `POST /api/quotes`: corpo `{ clientId, ownerId, description, total, status?, sentAt? }`; `status` só `draft` (padrão) ou `sent`; `total` maior que zero, até 2 casas; 201 com o orçamento. `clientId`/`ownerId` inexistentes: 422 com um erro por campo.
  - `PATCH /api/quotes/:id/status`: corpo `{ status, sentAt? }` (`sentAt` só com `sent`); 200 com o orçamento; 404 se não existe; 422 para transição não permitida. A origem da transição é o status efetivo: um `sent` parado só vai para `negotiating`, `won` ou `lost`.
  - `GET /api/indicators`: 200 com `{ "openTotal", "staleTotal", "conversionRate" }`, todos `number`. `openTotal`: soma de `total` dos orçamentos abertos (`sent`, `negotiating`, `no_response`); `staleTotal`: soma dos que a fila `/api/quotes/stale` lista; `conversionRate`: fração de 0 a 1, `won / (won + lost)`, ou `null` se nenhum orçamento foi ganho ou perdido.
  - `GET /api/quotes/:id/follow-ups`: 200 com `{ items: [{ id, quoteId, contactedAt, description }], total }`, do contato mais recente ao mais antigo; 404 se o orçamento não existe.
  - `POST /api/quotes/:id/follow-ups`: corpo `{ contactedAt?, description? }` (padrão de `contactedAt`: hoje; `description` vazia vira `null`, até 500); 201 com o follow-up; 422 em rascunho, data futura ou anterior ao envio; 404 se o orçamento não existe. Não altera o status do orçamento.
- **Variáveis de ambiente** (lidas de `../.env`): `DATABASE_URL` (obrigatória), `DATABASE_URL_TEST` (só testes de API), `PORT` (padrão `3333`), `CORS_ORIGIN` (origem que o navegador pode usar para chamar a API; passada a `createApp({ corsOrigin })`; sem ela, só mesma origem), `STALE_DAYS` (padrão `7`, mínimo `1`; vira `Config.staleDays`, passada a `createApp({ staleDays })` e usada pelo `quote-service`). No Docker Compose elas não vêm do `.env` de dev (que aponta para `localhost`): o `docker-compose.yml` define `DATABASE_URL` (host `db`), `CORS_ORIGIN` (`http://localhost:$WEB_PORT`) e as demais no `environment` do serviço.

## Decisões que moldam este código

- `app.ts` separado de `index.ts` para o supertest usar o app sem `listen` (AGENTS.md §5.2).
- `loadConfig` e `createApp` recebem env e `Pool` por parâmetro, sem singleton (AGENTS.md §5.2).
- Erro 500 não vaza stack nem mensagem interna; só o log do server vê o erro (AGENTS.md §12).
- Datas de calendário são strings `'YYYY-MM-DD'` (`CalendarDate`), como na API e nas colunas `date`; o domínio não usa `Date` para regra (AGENTS.md §5.5).
- "Hoje" e `staleDays` entram por parâmetro no domínio; nada lê relógio nem env (AGENTS.md §5.2, §8).
- `no_response` é derivado na leitura: só um `sent` parado vira `no_response` (`effectiveStatus`); não é gravado por job.
- O domínio não faz aritmética de dinheiro: `total` é string decimal vinda do `NUMERIC`; somas ficam no SQL (AGENTS.md §5.5).
- A normalização de `clients` acontece na rota (zod), antes do banco: o `UNIQUE` de `email` e `phone` compara o texto exato, então só e-mail em minúsculas e telefone só com dígitos fazem a duplicidade valer de verdade.
- A duplicidade vem da constraint (`23505`), sem checagem prévia, para não haver corrida entre inserts concorrentes; o repositório a traduz em `ValidationError` (422).
- Relógio e `staleDays` entram em `createApp({ now, staleDays })`; os serviços convertem `now()` em `CalendarDate` uma vez por chamada. Testes fixam os dois (AGENTS.md §8).
- Colunas `date` saem do SQL com `to_char(..., 'YYYY-MM-DD')`, para o `pg` não converter em `Date` com fuso.
- `total` do orçamento sai como `number` na API (o repositório converte o `NUMERIC`); não há aritmética de dinheiro no server.
- `quote-service` pré-checa `clientId` e `ownerId` com `existsById` para devolver 422 por campo (em vez de estourar a FK) e reporta os dois erros de uma vez.
- Em `PATCH .../status` a transição parte do status efetivo; já `createFollowUp` valida contra o status armazenado, então um `sent` parado ainda aceita contato.
- `GET /api/quotes/stale` é rota fixa declarada antes de `/quotes/:id`; do contrário o Express leria "stale" como id e responderia 404. A fila reaproveita `toResponse` e filtra por `isStale` em memória, sem query nova.
- Indicadores: as somas (`openTotal`, `staleTotal`) são feitas no SQL com `SUM ... FILTER` (exato para `NUMERIC`); o repositório só converte o resultado com `Number()` (AGENTS.md §5.5).
- "Parado" vem do domínio: `indicator-service` chama `listStaleQuotes` e passa os ids ao repositório, então o total parado não repete a regra e não pode divergir da fila.
- `getIndicators` faz duas leituras (a fila e os totais) sem transação: se um orçamento mudar entre elas, `staleTotal` pode destoar da fila por um instante. Aceito pelo volume e pelo uso (painel).
- Como a fila, os indicadores carregam todos os orçamentos para decidir quais estão parados; não há paginação nem filtro por responsável.
- Id de rota inválido (não numérico, zero, fora do inteiro seguro) responde 404, igual a um orçamento inexistente (`parseId`).
- `test/helpers/fixtures.ts` insere dados direto com SQL para preparar cada teste de API, sem passar pela API.
- Exige Node `^22.13 || ^24 || >=26` (`engines` no `package.json`), por causa do Vitest 5 e do ESLint 10.

## Como testar

Banco no ar (`docker compose up -d db`) e `.env` criado (`cp .env.example .env`).

- `npm --prefix server run test`: Vitest. Os testes de API (`routes/health.test.ts`, `routes/owners.test.ts`, `routes/clients.test.ts`, `routes/quotes.test.ts`, `routes/follow-ups.test.ts`, `routes/indicators.test.ts`) usam `DATABASE_URL_TEST` e falham de propósito se ela não existir; nunca usam o banco de dev (AGENTS.md §8).
- Os testes de API recriam o esquema do `climafacil_test` (`resetTestSchema`: recusa banco cujo nome não termine em `_test`, recria o schema `public` a partir de `db/init/001-schema.sql`) e limpam as tabelas (`clearTables`) entre os testes.
- `npm --prefix server run check`: `typecheck` + `lint` + `format:check` + `test`.
- Outros scripts: `dev`, `build`, `start`, `typecheck`, `lint`, `format`, `format:check`. Primeira vez: `npm --prefix server install`.
